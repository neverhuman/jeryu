This is a **fantastic** systems problem. The thing you want is not “code search” and not “duplicate-code detection” in the old lint sense. It is a **large-scale clone/concept-mining engine**: ingest many repos, normalize away names and formatting, detect repeated *implementation concepts*, cluster them, rank the biggest/highest-value repetitions, and hand the top clusters to an AI/human reviewer to decide whether a reusable Rust tool, library, CLI, codegen primitive, or codemod should replace them.

I did a broad sweep across papers, GitHub projects, official docs, forums/social sources, and practitioner discussions. Quora was not retrievable from here due robots blocking, and X results were mostly thin marketing snippets, so I would not treat either as a technical source. The strongest signal came from academic clone-detection literature, GitHub/Sourcegraph/GitHub Code Search architecture posts, and production-grade tools like Tree-sitter, Zoekt, Tantivy, ripgrep, Semgrep, CodeQL, Joern, ast-grep, SCIP, and SourcererCC/Siamese.

## My strongest recommendation

Build a **hybrid Rust engine** with four layers:

1. **Ultra-fast deterministic clone candidate generation** using normalized tokens, AST skeletons, API-call sequences, MinHash/SimHash, inverted indexes, and LSH.
2. **Structural refinement** using Tree-sitter ASTs, Merkle AST hashes, GumTree-style tree edit distance for top candidates, and optional lightweight data-flow/call-graph features.
3. **Cluster/rank repeated concepts**, not just clone pairs. Use connected components or Leiden/HDBSCAN-like clustering over candidate edges, then rank clusters by duplicated LOC, complexity, repo spread, churn, and fixability.
4. **AI review only after reduction**, never over raw repos. The AI gets “cluster dossiers”: representative snippets, normalized templates, diff/variance summary, call-site context, usage frequency, likely abstraction, risk, and candidate Rust replacement shape.

The core lesson from the literature is brutal: **do not start with embeddings or LLMs**. Start with indexed, deterministic, code-aware candidate generation. SourcererCC scaled clone detection with an optimized inverted index and token-ordering heuristics to avoid pairwise explosion; its evaluation reports scaling to 250 MLOC on a standard workstation. Siamese is even closer to your desired shape: multi-representation clone search, query reduction by token document frequency, incremental indexing, and results under 8 seconds on a 365 MLOC corpus. ([arXiv][1])

## Why this needs to be hybrid

Classic clone detection uses a taxonomy:

| Clone type |                            What changes | Best detectors                                           |
| ---------- | --------------------------------------: | -------------------------------------------------------- |
| Type 1     |                whitespace/comments only | hashing, token n-grams                                   |
| Type 2     |            identifiers/literals renamed | normalized token streams, AST shape                      |
| Type 3     |      added/removed/reordered statements | SourcererCC-style token sets, MinHash, AST edit distance |
| Type 4     | same behavior, different implementation | data-flow, graph features, embeddings, tests, AI review  |

Your phrase “regardless of structure and variable names” points at **Type 2 + Type 3 + some Type 4**, but the “largest repetitive code group” goal means you also need **cluster mining**, not just pair matching. The best practical system should collect many cheap signals, then refine only the promising edges.

There is also a major warning: semantic clone detection benchmarks are messy. A 2025 paper argues BigCloneBench has been misused for semantic clone evaluation and that many weak Type-3/Type-4 pairs are mislabeled, so high neural benchmark scores can be misleading. Treat ML models as **assistive rerankers**, not ground truth. ([arXiv][2])

## The architecture I would build

### 1. Repo ingestion layer

Use Rust with `gix`/gitoxide or libgit2 bindings for Git object access. Avoid repeatedly cloning and scanning full working trees when possible. For a huge corpus, store blobs content-addressed by BLAKE3 and map them to repo/path/commit spans.

Use Jeryu mirror hooks, configured forge webhooks, polling, or internal event streams for updates. The index should be **segment-based**: immutable committed segments plus a small mutable delta segment, exactly the pattern search engines use.

GitHub’s own code search story is relevant here: they built Blackbird, a Rust search engine designed specifically for code, because general text search did not handle code punctuation, regex, repository scale, and constantly changing data well. In beta, they described indexing 45 million repositories, 115 TB of code, and 15.5 billion documents. ([The GitHub Blog][3])

### 2. Parsing and chunking layer

Use **Tree-sitter** as the default parser. It is incremental, robust to syntax errors, general enough for many languages, and fast enough for editor keystroke-level parsing. That makes it ideal for your “scan once, then update live” requirement. ([GitHub][4])

Chunk at multiple granularities:

| Granularity               | Why                                                |
| ------------------------- | -------------------------------------------------- |
| file                      | cheap dedupe and vendored/generated code detection |
| function/method           | best abstraction unit                              |
| block/statement window    | catches duplicated inner logic                     |
| API-call trace            | catches repeated use-patterns                      |
| import/dependency context | helps identify tool/library opportunities          |

For Rust specifically, add a deeper optional path using `rust-analyzer`/HIR-style features later. Tree-sitter gets you fast syntax; compiler-level analysis gets you types and semantics.

### 3. Normalization/signature layer

For every chunk, produce a feature bundle:

```text
raw_hash
comment_stripped_hash
normalized_token_hash
token_ngrams
winnowed_fingerprints
minhash_signature
simhash_signature
AST_kind_sequence
AST_merkle_hashes
API_call_sequence
literal_shape_signature
control_shape_signature
optional: data-flow/call-graph features
optional: embedding vector
```

Normalization should replace identifiers and literals with role-aware placeholders:

```text
if user_id == nil { return Err(...) }
if account_id == nil { return Err(...) }

=> if ID_1 == NIL { return ERR_CALL(...) }
```

But keep some tokens untouched: library/API names, operators, control-flow keywords, error-handling constructs, SQL/HTTP/file-system calls, serialization calls, crypto calls, etc. Those are the “concept” anchors.

### 4. Candidate-generation indexes

You want **several indexes**, because no single representation finds all valuable repetition.

| Index                           | Purpose                                             |
| ------------------------------- | --------------------------------------------------- |
| exact hash index                | raw duplicates, generated/vendor detection          |
| normalized token inverted index | SourcererCC/Siamese-style scalable clone candidates |
| MinHash/LSH buckets             | near-duplicate token-set similarity                 |
| SimHash buckets                 | fuzzy similarity at massive scale                   |
| AST Merkle hash index           | repeated structures independent of names            |
| API-sequence index              | repeated usage patterns, “function-use waste”       |
| trigram/regex index             | fast fallback search and explanation                |
| vector ANN index                | semantic reranking, not primary retrieval           |

For full-text/regex code search pieces, study Zoekt and Google Code Search. Zoekt’s design uses positional trigrams and aims for sub-50ms results on huge codebases; its docs discuss incremental construction tradeoffs. Google’s Code Search lineage also emphasizes n-gram/token-index approaches over naive grep at scale. ([GitHub][5])

In Rust, **Tantivy** is the obvious Lucene-like building block for text/inverted indexing, and it supports incremental indexing. But for clone detection, I would not use Tantivy alone; I would use it alongside custom posting lists, Roaring bitmaps, compact binary feature stores, and LSH tables. ([GitHub][6])

### 5. Pair refinement

Candidate generation should produce maybe 10–500 candidates per chunk, not millions. Then refine with:

* weighted Jaccard over normalized token sets
* ordered n-gram overlap
* AST kind-sequence similarity
* AST tree edit distance only for close candidates
* API-call sequence alignment
* control-flow skeleton similarity
* optional data-flow similarity
* optional embedding cosine similarity
* optional LLM judgment only for final cluster summaries

GraphCodeBERT is relevant because it showed value in data-flow-aware code representation across code search and clone detection, but this should be a **reranking/modeling layer**, not your first-pass engine. ([OpenReview][7])

### 6. Clustering and “waste score”

The killer feature should be **cluster ranking**.

Every sufficiently similar pair becomes an edge:

```text
chunk_a -- similarity_score / reason --> chunk_b
```

Then cluster with connected components first; later use Leiden/Louvain or HDBSCAN-style clustering when clusters get too broad.

Rank clusters with something like:

```text
WasteScore =
  duplicated_LOC
  × log(instance_count + 1)
  × log(repo_count + 1)
  × avg_complexity
  × churn_weight
  × customer_surface_weight
  × abstraction_confidence
  × safety_confidence
```

A high-value cluster is not merely “duplicated code.” It is duplicated code that is large, repeated across repos, changed often, risky, boring, and abstractable.

### 7. AI handoff format

For each top cluster, generate a dossier:

```text
Cluster ID: C-2026-004281
Theme: repeated HTTP retry/backoff wrapper
Instances: 184
Repos: 37
Duplicated LOC: 11,420
Median function size: 52 LOC
Churn last 90 days: high
Similarity basis: API sequence + normalized AST + token MinHash
Common APIs: reqwest, tokio::time::sleep, exponential backoff, tracing
Variance:
  - retry count: 3/5/10
  - jitter: present in 28%
  - error mapping: 6 variants
Suggested Rust replacement:
  crate/module: veox_retry
  function: retry_async<T, E, F>
  codemod feasibility: medium-high
Risk:
  business-specific error handling in 14 instances
Representative snippets:
  ...
```

This is exactly the unit an AI reviewer can reason over.

## What I would not do

I would **not** build “a vector database over all functions” and call it done. That will be expensive, noisy, hard to explain, and weaker than deterministic signatures for Type 1–3 clones.

I would **not** run CodeQL/Joern over every repo as the first pass. Excellent for deep refinement, too heavy for primary discovery.

I would **not** rely on line-level duplicate detectors. They are useful baselines, but your goal is concept mining across renamed, reshaped, partially modified code.

I would **not** send raw codebases to an LLM. Send ranked cluster dossiers after compression.

## Incremental/realtime design

The incremental model should be content-addressed:

1. Webhook or filesystem watcher receives repo update.
2. Resolve changed commits/files.
3. For each changed file, compute blob hash.
4. If blob hash already known, reuse parsed chunks and signatures.
5. If new, parse with Tree-sitter and extract chunks.
6. Delete old chunk IDs for that repo/path/commit view.
7. Insert new chunk docs into mutable delta indexes.
8. Recompute candidate edges only for affected chunks and their buckets.
9. Update affected clusters.
10. Periodically compact immutable segments and rebuild cluster graph to clean up deletions.

Be careful with union-find: it is great for adding edges, bad for deleting edges. For realtime correctness, keep an edge store and recompute connected components for affected buckets/clusters, plus schedule periodic full cluster rebuilds.

## MVP plan

**Phase 1: deterministic clone miner.**
Support 5–10 languages via Tree-sitter. Extract functions/blocks, normalize tokens, build MinHash/SimHash/AST signatures, cluster Type 1–3 clones, and output top waste clusters.

**Phase 2: repo-scale incremental engine.**
Add Git object reuse, webhook updates, delta indexes, deletion handling, and cluster dossiers.

**Phase 3: semantic enrichment.**
Add API-sequence mining, call graph features, SCIP/rust-analyzer imports, embeddings for rerank/labeling, and LLM review.

**Phase 4: replacement workflow.**
For each approved cluster, generate a Rust abstraction proposal, codemod strategy, test strategy, risk report, and rollout plan.

## Final recommendation

Build it as a **SourcererCC/Siamese-inspired Rust clone-search engine + Tree-sitter structural index + cluster-ranking system + AI dossier reviewer**.

The secret sauce is not one model. It is the **feature bundle** per code chunk and a ruthless, staged narrowing pipeline:

```text
many repos
→ content-addressed chunks
→ normalized multi-representation signatures
→ cheap indexed candidate generation
→ structural/API/data-flow refinement
→ concept clustering
→ waste ranking
→ AI/human abstraction decision
→ custom Rust tool/codemod proposal
→ incremental update forever
```

That is the system I would bet on. It is fast, explainable, scalable, incrementally maintainable, and it gives the AI the right job: judging the most valuable repeated concepts, not wandering through millions of files.
