# Release Process

This document governs release of the Jeryu tool control plane and promotion of
its Jankurai authority. It does not authorize Jain candidate metadata, formal
GA, public routing, or an external package publication.

## Version and source authority

The crate version is sourced from the workspace `Cargo.toml`. The governed
Jankurai version and every source/build identity are sourced from
`tool-manifest.toml` on protected `jeryu-tool/main`. `CHANGELOG.md` records
operator-visible changes. Immutable source and release tags never move; a
correction uses the next linear tag.

## Preconditions

- The canonical checkout is clean, on one claimed branch based on current
  protected main, and has no registered worktrees or sibling source overrides.
- `ops/render-tool-manifest.sh --check` reports no generated drift.
- `just` passes with the governed binary: fast, check, score, and security.
- Exact-head required CI passes in an automatically removed `clone --no-local`
  sandbox and is read back from `git.neverhuman.org` at the full published SHA.
- Branch protection still requires linear history, the exact required context,
  enforced administrators, and one approval from an identity other than the
  author.
- The immutable source tag, source commit/tree, archive SHA-256, Cargo lock
  SHA-256, vendor inventory, builder image, build context, binary SHA-256, and
  protected manifest identity all match the proposed release evidence.

## Reviewed release procedure

1. Change authored authority only in `tool-manifest.toml` and related authored
   policy, then run the renderer for every declared consumer.
2. Commit generated results with the authority change. Publish the exact branch
   non-force, open a protected PR, and run exact-head required CI.
3. Read back all checks and protection. A reviewer other than the author reviews
   source, generated bytes, and evidence before approval. A non-author performs
   the fast-forward merge.
4. Read back protected main and cut the next unused immutable release tag at that
   exact commit. Record commit, tree, checksums, and review/CI evidence.
5. Build and install only from the merged protected identity. The installer must
   reproduce the declared binary, preserve the existing binary as a
   content-addressed backup, publish atomically, and write a path-bound receipt.
6. Verify the installed version, digest, physical path, receipt, and the first
   consuming proof before releasing the coordination boundary.

## Release gate and launch gate

The release gate requires security scans, immutable provenance, the prior binary
backup, tested rollback, consumer monitoring, and operator stop conditions. The
launch gate also confirms rate limit or abuse controls at every exposed runtime
boundary. `jeryu-tool` itself opens no network service, so request rate limiting
is not applicable here; its abuse controls are strict filesystem custody,
single-writer claims, fixed forge transport, credential isolation, offline
builds, and fail-closed receipt verification. A consuming service must prove its
own rate limits and abuse controls before it adopts the new authority.

Monitoring consists of installation receipt verification, binary digest/version
readback, renderer drift checks, required-check state, intrinsic Jankurai proof,
and the first consumer's health/proof result. Do not declare the release complete
from a successful build alone.

## Rollback

Before replacement, the installer stores the current physical binary under its
SHA-256 in the governed rollback directory and records that path in the new
receipt. Rollback restores only a previously verified immutable binary and its
matching path-bound receipt. It never moves a tag, edits a score row, rewrites
history, or substitutes a same-version binary with a different digest.

If a broker and auditor pin become skewed, freeze ref mutations and use an
explicit reviewed boundary transition. A temporary rollback must be scoped,
receipt-valid, read back from inside the consumer boundary, and reverted on the
first failed assertion. After restoration, verify both host and consumer views
plus service health before releasing the freeze.

## Stop conditions

Stop without publishing or retrying when any checkout is dirty, protected main
moves, a required check is missing/red, review identity is not independent,
renderer output drifts, a digest or receipt differs, an offline input is absent,
the service cannot return healthy, or a forge mutation is ambiguous. Preserve
the terminal evidence and resolve the authority boundary; do not bypass the
gate, weaken a policy, or manually replace a proof result.
